## Family: Strimer Plus (wired)

**Source folder:** `LConnectCore/Products/StrimerPlus/`
**Marketed name(s):** Lian Li Strimer Plus — RGB cable extensions for ATX 24-pin / VGA 8-pin / VGA-triple. LED-only addressable lighting strips, no fans, no LCD, no sensors.
**ControllerTypeID enum value(s):** `StrimerPlus = 16801792` (`L-Connect.Core/LConnectCore/Devices/ControllerTypeID.cs:15`). Class bucket: `ControllerClass.StrimerPlus = 6` (`L-Connect.Core/LConnectCore/Devices/ControllerClass.cs:13`). Class-mask constant `ClassStrimerPlus = 24576` (`L-Connect.Core/LConnectCore/Devices/ControllerTypeIDDefinitions.cs:39`).
**USB VID:PID:** `0x0CF2:0xA200` (decimal `3314:41472`) — `L-Connect.Core/LConnectCore/Devices/KnownDevices.cs:35`. (Distinct from the Galahad / HydroShift VID `0x0416` and the SL/AL fan family VID `0x0CF2`; same VID as SL/AL/TL fans, different PID range `0xA2xx`.)
**Framing classes used:** none of the LCDV2 A/B/C framings — Strimer Plus uses a flat **HID Feature-Report** path for control packets and a flat **HID Output-Report** path for per-LED RGB data, with **`ReportID = 0xE0`** as the leading byte and a single-byte command code in `data[1]` whose low 4 bits sometimes encode a port index (`StrimerPlusDevice.cs:11`, `129-145`, `147-163`, `165-168`).
**Phase 0d status:** not in scope (different USB vendor/PID and protocol from LCDV2). Static-analysis only for this survey.

**Subsystem fingerprint:**
- Sensors / handshake: no — there is no `GetHandshakeInfo`-equivalent. Only firmware version and a Channel-2 port-count probe (4 or 6 ports) are read back (`StrimerPlusDevice.cs:61-89`).
- Fan PWM / pump PWM / fan curve / temperature: **N/A** — Strimer Plus carries no fans, no pump, no thermistors. Confirmed by absence of any PWM, RPM, temperature, or fan-curve API on `IStrimerPlusDevice` (`StrimerPlusDevice.cs/IStrimerPlusDevice.cs:7-28`).
- LCD on/off / brightness / rotation / frame upload: **N/A** — no LCD subsystem. No `LCDControl`, `SendJpeg`, `SendH264Frame`, or analogue exists on the interface.
- Lighting (preset effect modes): **yes** — `SetEffectSetting(port, mode, speed, direction, brightness)` writes a 6-byte feature-report packet selecting one of 24 catalogued lighting modes split between two scopes (`Individual` per-port, `Complete` synchronized across all ports) (`LightingMode.cs:5-32`, `LightingScope.cs:5-10`, `Constants.cs:23-52`, `StrimerPlusDevice.cs:165-168`).
- Lighting (per-LED RGB writes): **yes** — `SetColorSetting(port, Color[])` streams up to 27 RGB triples per port over an HID Output report. Caveat: bytes are emitted as **R, B, G** (not R, G, B) on the wire (`StrimerPlusDevice.cs:129-145`, `Constants.cs:18`).
- Effect-enable / port mask: yes — `SetEffectEnable(port, multiPort)` either enables a single port (low 4 bits = port index, 0..=11) or, when `port >= 12`, switches into **multi-port mask** mode where a 12-bit `PortFlags` bitmap selects any subset of the 12 ports (`StrimerPlusDevice.cs:147-163`, `PortFlags.cs:5-27`).
- Frame counter: yes — `GetFrame` reads a BE-u16 frame counter; `SetFrame` writes one with constrained valid ranges (`StrimerPlusDevice.cs:91-100`, `170-179`). Purpose / role unclear from static analysis alone (animation playback cursor? sync token?). Flagged 🚧 below.
- Continuous re-issue pattern: not observed in `StrimerPlusDevice.cs`; service-layer behaviour not inspected for this survey. Note: `WriteDelayTime` defaults to **40 ms** between every feature/output report, and `ReadTimeout=10 ms`, `WriteTimeout=1000 ms` (`StrimerPlusDevice.cs:53-59`, `115-127`). This is much larger than LCDV2's per-write pacing and is a notable family-level divergence.
- Reset / soft-reset: not present. No `ResetDevice`-equivalent on `IStrimerPlusDevice`.
- Firmware upload / activation: not present. Only `GetFirmwareVersion` (read-only) is exposed.
- Crypto / obfuscation at HID transport: none observed in `StrimerPlusDevice.cs`. Plain-byte feature/output reports throughout.

### Commands

Strimer Plus does **not** use the LCDV2 single-byte `Command` enum at offset 1. Instead, the byte at `data[1]` is a *command-and-port composite* with this static-analysis layout (high nibble = operation, low nibble = port index where applicable):

`RequestType` enum has only three nominal entries — `FirmwareVersion`, `Channel2PortCount`, `EffectSetting` (`RequestType.cs:5-10`) — and `SettingType` is a per-port discriminator `Port0..Port11` (`SettingType.cs:5-19`). Neither enum is consumed inside `StrimerPlusDevice.cs`; both are presumably used by an upper-layer dispatcher (e.g., a controller / UI binding) outside this folder.

### Subsystem patterns

- **Single transport, two HID directions:** every read and almost every write goes through HID **Feature reports** (`SendFeatureReport` / `GetInputReport`), with `ReportID = 0xE0` as `numArray1[0]` and a 64-byte input-report data area (`StrimerPlusDevice.cs:13`, `102-113`, `115-120`). The one exception is the per-LED RGB stream, which uses **HID Output reports** (`HidDevice.Write`, `StrimerPlusDevice.cs:122-127`, called only from `SetColorSetting`). This is a meaningful protocol-level divergence: bulk LED data has its own transport class on this device.
- **Command-byte = operation high nibble + port low nibble:** the device packs a 4-bit operation tag and a 4-bit port index into `data[1]`. Operation tags observed: `0x10` (set effect params), `0x20` (set effect enable / multi-port mask), `0x30` (set per-LED colors), `0x50` (read firmware / read channel-2 port-count), `0x55` (read frame counter), `0x60` (set frame counter). Port index is 0..=11; the magic value 12 (= `0x0C`) on the `0x20` operation switches to multi-port-mask mode.
- **Two-channel × six-port topology:** Channel 1 is hard-coded to 6 ports (Port0..Port5). Channel 2 is either 4 or 6 ports depending on SKU (`GetChannel2PortCount` returns 4 or 6); ports 6..=11 are populated accordingly (`Constants.cs:12-20`, `PortFlags.cs:5-27`). The `PortFlags` enum exposes pre-baked masks `Channel1 = 0x003F`, `Channel2_4 = 0x03C0`, `Channel2_6 = 0x0FC0`, `All = 0x0FFF` for use with the multi-port-mask form of `SetEffectEnable`.
- **Two lighting scopes:** `LightingScope.Individual` (effect runs per-port independently) vs `LightingScope.Complete` (effect synchronized across all participating ports). The `LightingMode` enum splits cleanly into `*_Individual` (13 modes) and `*_Complete` (11 modes), and `Constants` populates two separate `HashSet<LightingMode>` for runtime classification (`Constants.cs:23-52`). The wire interface itself is unaware of scope — the host picks a `mode` byte that is by convention either Individual or Complete; the device acts on it.
- **Lighting (preset) tuple:** `(mode, speed, direction, brightness)` — fits in 4 bytes after the 2-byte header. No RGB color slots are part of `SetEffectSetting` itself; per-LED colors arrive separately via `SetColorSetting` (`0x30\|port`). This is *both* a preset-mode device *and* a per-LED-write device, with the two paths composable per port.
- **Pacing:** `WriteDelayTime` default = 40 ms, applied via `Thread.Sleep` after every feature **and** output write (`StrimerPlusDevice.cs:53-59`, `115-127`). The constructor sets `ReadTimeout = 10 ms`, `WriteTimeout = 1000 ms`. This is roughly an order of magnitude slower than the LCDV2 cadence and meaningfully constrains per-LED frame rate (worst case: 12 ports × ≥40 ms = ~480 ms per global recolor — though Channel-2-mask multi-port semantics are for effect-enable, not for per-LED writes, so a daemon doing per-LED animation must serialize 12 separate output reports per "frame").
- **No service-side continuous re-issue observed in this folder.** The frame-counter pair `GetFrame`/`SetFrame` *might* be the device's own animation-cursor and could be the analogue of LCDV2's continuous-re-issue pattern, but this is speculation pending live capture.
- **Sentinel-byte firmware-validity check** (`FirmwareVersion.cs:78`): four hardcoded magic bytes (`0xE0, 0x52, 0xFF, 0x40`) must match exactly for the firmware response to be considered valid. This pattern is a useful spoof / wrong-device guard — different from LCDV2's PacketNumber-based demux.
- **Crypto:** none at the HID transport. Plain bytes throughout, consistent with LCDV2.

### Notable divergences from LCDV2

- **No A/B/C `CommandPacket` framing.** No 64-byte report-1 envelope with `Length` and `PacketNumber` fields, no 1024-byte multi-packet bulk write envelope. Strimer Plus uses HID Feature reports for control and HID Output reports for LED data, both with a flat byte layout. This is a *fundamentally different transport* from LCDV2 even though both are HID.
- **No 1-byte `Command` enum at offset 1.** The byte at `data[1]` is a *composite* of operation tag (high nibble) and port index (low nibble). No equivalent of the `Command::GetHandshakeInfo = 0x81` byte-aligned enum exists.
- **Subsystem coverage is lighting-only.** Confirmed absent: handshake (no `GetHandshakeInfo`), pump PWM, fan PWM, fan curve, temperature, LCD control / frame, reset, firmware upload. Present: per-port preset effect (`SetEffectSetting`), per-LED RGB (`SetColorSetting`), effect-enable + port mask (`SetEffectEnable`), frame counter (`GetFrame` / `SetFrame`), firmware-version read, channel-2 port-count read.
- **Different USB VID.** `0x0CF2` (Lian Li shared with the SL/AL/TL fan families) vs LCDV2's `0x0416` (Winbond/Lian Li for the AIO family).
- **Different `ReportID`.** `0xE0` (224) vs LCDV2's `0x01` (A-framing) / `0x02` (B-framing) / `0x03` (C-framing).
- **Per-LED transport uses HID Output reports**, while every other Strimer Plus operation — and *all* LCDV2 operations covered so far — uses HID Feature reports.
- **R, B, G byte order on per-LED writes.** Unique among the families surveyed in Phase 0e so far. May be a firmware quirk or a long-standing C#-side swap; live capture against real hardware will resolve it.
- **`LightingSpeed` non-monotonic encoding.** `Faster=255, Fastest=254, Normal=0, Lower=1, Lowest=2`. The high-speed values are at the top of the byte range; the slow values cluster at the bottom. A naive `0..=255 -> percent` mapping in a Linux daemon will *invert* the user's expected speed for any value in the 3..=253 range.
- **Pacing.** Default 40 ms `WriteDelayTime` per call; LCDV2 lives in the few-ms regime. A daemon doing per-LED animation will need to either lower `WriteDelayTime` (test for firmware tolerance) or accept ~25 LED-writes/sec ceiling per port.

### Cross-cutting note: OpenRGB overlap

Strimer Plus is the family in this snapshot that most closely fits OpenRGB's target profile (RGB-only, per-LED addressable, pre-baked effect modes). The composite-command-byte layout, the R-B-G byte order, the `0xE0` ReportID, and the 12-port topology are all distinctive enough that an OpenRGB driver — if one exists for this VID/PID `0x0CF2:0xA200` — will be the cleanest external cross-check for the static-analysis findings above. **Pre-flagged for the parallel P0e-14 OpenRGB cross-validator pass.**

### Wireless variant relationship (high level)

A separate, **wireless** Strimer Plus exists at `LConnectCore/Products/LWireless/StrimerPlus/` (`StrLightingConfig.cs`, `StrSeparateLightingConfig.cs`, `FirmwareVersion.cs`). It uses different types from the `slv3.models` namespace (`RFBrightnessType`, `RFLampEffectSpeedType`, `EffectDirections`, `EffectScopes`, `StrEffects`) and is bound by a `MacStr` (MAC address string), implying a radio-relayed transport via the Wireless Controller hub rather than direct HID to the Strimer Plus board (`LWireless/StrimerPlus/StrLightingConfig.cs:36-67`). The wired and wireless variants share *concepts* (lighting mode, scope, brightness, speed, direction, per-port colors) but **not** the wire format documented above. Detailed survey of the wireless side is out of scope here and is being handled by the parallel LWireless task.

### Open questions / unclear from static analysis

- 🚧 **Per-LED color byte order is R, B, G** in `SetColorSetting` (`StrimerPlusDevice.cs:140-142`: indices `[2 + i*3] = R`, `[2 + i*3 + 1] = B`, `[2 + i*3 + 2] = G`). Is this (a) a long-standing C#-side bug that the firmware secretly compensates for, (b) the firmware genuinely expects RBG, or (c) a JustDecompile artefact? Live capture comparing the host bytes vs the rendered LED colour will resolve this; until then, a Linux port should mirror the C# byte order to preserve compatibility with installs that already have user palettes saved.
- 🚧 **`SetFrame` / `GetFrame` semantics.** The frame counter is BE u16, written via op `0x60` and read via op `0x55 / sub 0x05`. The valid-range gate in `SetFrame` (`StrimerPlusDevice.cs:174-177`) — rejecting `hi > 0`, `lo < 15`, `60 < lo < 80`, or `lo > 235` — is suspicious: `hi==0` confines the value to `0..=255`, and the disallowed bands carve out `lo ∈ {0..=14, 61..=79, 236..=255}`. Plausible interpretations: (a) FPS / refresh-rate setpoint with hardware-disallowed bands, (b) animation-cursor upper bound, (c) unrelated mode field repurposing the 16-bit slot. Cannot disambiguate from static source.
- 🚧 **`FirmwareVersion.GetVersion` decoding.** `(FineTune >> 4 & 0xF) + 1` and `FineTune & 0xF`, with the low nibble required `<= 9`, then `(major+1)*10 + (minor-3)`. The `-3` offset is opaque. Until live capture, treat the decoded `Version` as an opaque comparator; do not surface the decoded number to users without verification.
- 🚧 **`SetEffectEnable` payload-byte 2-3 in single-port mode.** Both bytes are explicitly zeroed in the `port < 12` branch (`StrimerPlusDevice.cs:152-154`). Does the firmware accept other values, ignore them, or reject the packet? Affects whether a daemon can pack additional metadata into the same 4-byte report.
- 🚧 **Effect-enable persistence.** Whether `SetEffectEnable` for a port subset *disables* the unmasked ports, or *enables* the masked ports without affecting the others, is not annotated in the source. The naming ("Enable") and the multi-port-mask form suggest the former (mask = enabled set); to be confirmed live.
- 🚧 **Number of LEDs per port.** `Constants.MaxLEDCountPerPort = 27` is the host-side cap, but actual LED counts vary by Strimer Plus SKU (24-pin extension vs 8-pin VGA vs triple-VGA, etc.). The wire format does not appear to advertise per-port LED counts; presumably the host application configures this via UI / saved profile. Linux port will need an explicit per-port LED-count config.
- 🚧 **Pacing tolerance.** Whether `WriteDelayTime = 40 ms` is a firmware requirement or a conservative C# default is unknown. Live testing at lower delays will tell us how fast per-LED animation can run on this family.
- 🚧 **`SettingType` / `RequestType` consumers.** Neither enum is referenced inside the StrimerPlus product folder; they are defined but inert here. The dispatcher that maps these to wire commands lives elsewhere (presumably in a `Controller` / `Service` layer not part of the protocol-only survey).

### Recommendation

Strimer Plus is a clean, lighting-only family with a substantially different transport from LCDV2. The codec layer for it should be a separate module (likely `crates/protocol/src/strimer_plus.rs` or its own crate) — *not* a parameterisation of the LCDV2 A/B/C `CommandPacket` machinery. The two highest-priority unknowns to resolve before any write goes to a real device are (1) the R-B-G byte order on per-LED writes and (2) the `SetFrame` valid-range semantics, since both have plausible interpretations that produce visibly wrong output if guessed.
