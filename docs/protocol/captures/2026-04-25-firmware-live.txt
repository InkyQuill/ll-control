# Notable findings during verification (different from decompiled C# expectations):
# =============================================================================

# Finding 1 — Unsolicited cmd-0x8e (=142, ResetDevice's code) status packet.
#   On the very first firmware command after device idle, an extra packet
#   `01 8e 00 00 00 01 02 00 ...` appears in the read queue. Length=1,
#   Data=[0x02]. The command byte (0x8e) is the ResetDevice opcode, but
#   we never sent a reset. Hypothesis: this is a queued unsolicited
#   notification (boot ack? thermal status? unknown). Subsequent runs do
#   NOT see this packet. The verify-galahad harness drains stale packets
#   before sending the firmware request to avoid confusion.
#
# Finding 2 — Datetime packet (PacketNumber=1) is unreliable on FW 1.6.
#   The decompiled `Galahad2VisionDevice.cs:88-105` reads two ACommandPackets
#   back-to-back, expecting the first to be the version string and the second
#   to be a build-datetime string. Real-hardware observation shows:
#     * The version packet (PacketNumber=0) arrives reliably within ~10ms.
#     * The datetime packet (PacketNumber=1) arrived ONCE during the entire
#       verification session — as an async leftover between runs, with content
#       "Oct 30 2025,17:01:18". Subsequent same-session firmware requests do
#       not produce a fresh datetime packet within a 1s read window.
#   Working theory: the device sends the datetime packet at most once per
#   USB-attach (boot/enumerate ack) or some similar lifecycle trigger.
#   Worth re-investigating after a power cycle (Phase 0c task).
#
# Finding 3 — PacketNumber field MUST be used to distinguish multi-packet
#   responses. The decompiled C# reads sequentially without checking
#   PacketNumber, which is fragile against unsolicited interleaved packets.
#   The Rust harness filters by both `cmd echo == 134` AND `PacketNumber`,
#   which is more robust.
