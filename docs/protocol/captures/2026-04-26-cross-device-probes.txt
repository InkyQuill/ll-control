## Methodology

This is the cross-device probe set for Phase 0e. Each candidate
targets a hypothesis sourced from a sibling device family's command
table - most have a transient-vs-stored split visible in their C#
source that LCDV2 may or may not also implement.

The CLI gate at `verify-galahad probe ... --yes-read-only` makes
every probe a deliberate, manually-confirmed action. Each entry below
must be hid-safety-reviewer-cleared as **APPROVED** before any byte
hits the device.

Probe set size: at most 8 entries. The cap exists because a longer
list incurs review fatigue and increases the chance one gets run by
mistake. This drafted list contains 6 entries.

### Selection rationale

Candidates are drawn from three sibling families with the most
applicable surfaces:

1. **Galahad II Trinity** (`0x0416:0x73A3` / `0x73A4`) - same MCU
   vendor as LCDV2 (Winbond/Nuvoton VID 0x0416) and the closest
   sibling product line. A-class framing layout is byte-identical to
   LCDV2 (`Galahad2Trinity/ACommandPacket.cs`). Any read-only opcode
   declared on Trinity has the highest prior probability of eliciting
   a real response on LCDV2 firmware.
2. **HydroShift LCD (HS I)** (`0x0416:0x7398..0x739A`) - same MCU
   vendor, same A/B/C trio of framing classes, byte-for-byte
   identical layouts (`HydroShiftLCD/ACommandPacket.cs`,
   `BCommandPacket.cs`, `CCommandPacket.cs`). HS I shares cmd 14
   `SendJpeg` and cmd 15 `UploadJpeg` enum entries with LCDV2 but
   adds cmd 22 `UploadStartupAviMovie` (write-side, excluded) - the
   `Startup` qualifier closes the cmd-15-as-stored-image hypothesis at
   the naming-convention level (see `cross-device-survey.md` section
   6.2). HS I declares no LCD-state-query cmd LCDV2 lacks.
3. **TLLCD** (`0x04FC:0x7393`) - different MCU vendor (Sunplus), so
   priors are lower than for same-MCU siblings, but TLLCD is the only
   sibling whose enumerated handshake-equivalent (`cmd 60
   GetHandshakeInfo`) returns LCD playback state (`Mode` + `FrameIndex`)
   rather than fan/pump telemetry. That makes it the highest-value
   candidate for the cmd-15 activation question even though the cross
   -MCU prior is low. Probing costs almost nothing if it doesn't
   respond (the existing `probe` drain logic discards stale bytes).

### Excluded candidates and why

The following sibling commands were considered but excluded:

- **HS I cmd 22 `UploadStartupAviMovie`** - direct cmd-15 sibling and
  the strongest cross-device evidence of stored-image semantics, but
  the `Upload*` prefix marks it a write to non-volatile storage. Out
  of scope for the read-only probe set.
- **Trinity cmd 135 `LEDTestMode`** - name is ambiguous (no
  `Get*`/`Set*` prefix) and the only hint of semantics is the
  `LEDTest` analogue in LCDV2's `LCDControlMode`, which is a *toggle*
  on the LCD test pattern - i.e., write-side. Conservative read: it
  mutates LED display state. Excluded.
- **Trinity cmd 137 `WriteSerialNumber`** / **HS I cmd 137 / LCDV2
  cmd 137 `SetSerialNumber`** - destructive on identity bytes. Hard
  exclusion.
- **HS I cmd 18 `UploadAvi` / cmd 19 `UploadH264` / cmd 21
  `UploadH264Info`** - all `Upload*` writes to non-volatile or
  decoder buffers. Excluded.
- **TLLCD cmd 70 `WriteSYNCJPG` / cmd 71 `WriteBootAVI` / cmd 72
  `WriteBootJPG`** - explicit `Write*` prefix, write-side. Excluded.
- **HS I cmd 23 `IsLCDAvailable`** - already verified live on LCDV2
  (see `docs/protocol/galahad2-lcdv2.md:748-785`); re-probing would
  add no information. Excluded under priority rule 4.
- **All slv3-SDK and lcd207-SDK opcodes** (`PushJpg=0x65`,
  `UpdateFireWare=0x28`, `RF_*` family, etc.) - LCDV2 does not go
  through those SDKs (per the Phase 0e plan); their wire framing is
  DES-enveloped and does not match the A/B/C HID classes. Out of
  scope.
- **Speculative gap-byte probes (cmd 16, cmd 17, cmd 24..127, cmd
  135, cmd 140, cmd 141, cmd 143..)** - mentioned in
  `cross-device-survey/per-family/hydroshift-lcd.md:372-375` as
  "unenumerated bytes the firmware could honour." Without a sibling
  citation pinning specific bytes, blind enumeration is fishing
  outside the IP boundary and outside this drafting task's scope.
  Excluded; revisit only if every cited candidate fails to respond.

### Probe 1: Trinity GetFanPumpParams capability query (A-class)

**Cmd byte:** 0x8C (decimal 140)
**Framing class:** A
**Source family / hypothesis:** Galahad II Trinity. Trinity's
`Commands.cs` enum extends one byte past LCDV2's surface (LCDV2 stops
at cmd 139 in the 130s block, then jumps to cmd 142 `ResetDevice`;
Trinity has cmd 140 `GetFanPumpParams` filling that gap). Same MCU
vendor (Winbond/Nuvoton) and same A-class framing. Likely returns
firmware-side fan/pump RPM ranges and PWM bounds - which on LCDV2 are
currently hardcoded host-side. If LCDV2 silently honours this opcode,
the response would be a capability block we currently do not query.
**Citation:** `L-Connect.Core/LConnectCore/Products/Galahad2Trinity/Commands.cs:18`
(enum entry `GetFanPumpParams = 140`); cross-referenced in
`docs/protocol/cross-device-survey/per-family/galahad2-trinity.md:45`
("Defined; no caller in device class. Likely returns RPM ranges and
PWM bounds").
**Read/write classification:** read (`Get*` prefix; no caller exists,
so the C# code never *writes* a value via this byte; sibling family
classifies it host->device + device->host on the same A-class shape
LCDV2's other read commands use)
**Why we expect this to be safe:** A-class bare request (`Length=0`,
empty Data) is the same shape LCDV2 already accepts for cmd 129
`GetHandshakeInfo`, cmd 130 `GetPumpLightingInfo`, cmd 132
`GetFanLightingInfo`, cmd 134 `GetFirmwareVersion`. Worst case the
firmware ignores the byte and we get a timeout or stale bytes that
the existing `run_probe` drain logic discards
(`tools/verify-galahad/src/probe.rs:264-280`). No write payload is
sent.
**Expected response shape if hypothesis holds:** A-class echo with
`Length>0` and a small Data block carrying RPM min/max + PWM bounds
(per Trinity per-family staging line 86: "likely a structure carrying
RPM min/max and PWM step info").
**Failure mode if hypothesis fails:** Either (a) bare echo with
`Length=0` and zero Data, (b) no response within the 500 ms read
timeout, (c) stale unsolicited cmd-129 / cmd-0x8E packets that the
drain loop discards.
**Run command:** `cargo run -q -p verify-galahad -- probe 0x8C --framing a --yes-read-only`
**hid-safety-reviewer classification:** APPROVED
**hid-safety rationale:** Galahad2Trinity/Commands.cs:18 declares GetFanPumpParams=140 (enum entry only; no caller in Galahad2TrinityDevice.cs — cmds 129/131/133/134/138/139 are the only ones dispatched). Galahad2Vision/Commands.cs has no cmd 140 entry. A-class framing correct: all Trinity 130s-block commands use single 64-byte A-class packets. Zero-filled payload offsets 2+ have no documented sub-command meaning on any sibling family. No write side effect possible.

### Probe 2: TLLCD GetHandshakeInfo - LCD playback state query (B-class)

**Cmd byte:** 0x3C (decimal 60)
**Framing class:** B
**Source family / hypothesis:** TLLCD. TLLCD's `cmd 60
GetHandshakeInfo` returns a 3-byte response carrying `Mode` (u8) and
`FrameIndex` (BE u16) - i.e., the **current LCD playback mode and
frame position**. This is the only sibling-family query that returns
LCD-state telemetry rather than fan/pump telemetry, which makes it the
single highest-value candidate for the cmd-15 activation question. If
LCDV2 firmware honours this byte (or any byte returning equivalent
state), we get a direct read of "what is the LCD currently
displaying" - with which we could verify cmd-15 stored-slot activation
without a power-cycle. TLLCD uses a different MCU vendor (Sunplus
0x04FC vs LCDV2's Winbond 0x0416), so the cross-MCU prior is lower
than for Trinity / HS I, but the upside justifies the probe.
**Citation:** `L-Connect.Core/LConnectCore/Products/TLLCD/LCDCommands.cs:13`
(enum `GetHandshakeInfo = 60`); response shape at
`L-Connect.Core/LConnectCore/Products/TLLCD/HandshakeInfo.cs:29-44`;
cross-referenced in
`docs/protocol/cross-device-survey/per-family/tllcd.md:148, 198-211`.
**Read/write classification:** read (TLLCD source: bare request with
`Length=0`, response is structured 3-byte status block).
**Why we expect this to be safe:** Bare request with empty payload.
TLLCD probes via the same B-class ReportID (0x02) that LCDV2 uses for
B-class. The TLLCD T-class reads only 64 bytes (vs LCDV2 B-class's
512), but the request-side shape is identical: `[ReportID=0x02, Cmd,
DataSize=0, PacketNumber=0, Length=0, zero-pad]`. If LCDV2 firmware
doesn't recognise the byte, the worst case is no response or a stale
echo with `bytes[1] != 0x3C` that the drain logic catches.
**Expected response shape if hypothesis holds:** B-class echo with
`Length>=3`, Data[0] = current LCDControlMode, Data[1..3] = BE u16
frame-index or similar state counter. Even if the LCDV2 firmware
returns a *different* shape, any non-empty response bytes hint at
whether the byte means anything to LCDV2 firmware.
**Failure mode if hypothesis fails:** Echo with `Length=0` (LCDV2
acknowledges the byte but has no data to return), no response
within the 500 ms read timeout, or stale-cmd-byte response discarded
by the drain.
**Run command:** `cargo run -q -p verify-galahad -- probe 0x3C --framing b --yes-read-only`
**hid-safety-reviewer classification:** NEEDS-CLARIFICATION
**hid-safety rationale:** TLLCD/TLLCDDevice.cs:121-134 confirms cmd 60 is a pure read. Framing concern: TLLCD LCDPacket.cs declares PacketLength_Output=512, not 64 as the probe doc states. The probe sends LCDV2 B-class (1024 bytes, ReportID 0x02) which is a different shape than TLLCD T-class (512 bytes). Cmd 60 not in LCDV2 enum. What is needed: confirm intent is to send LCDV2 B-class (1024 bytes) and observe LCDV2 response; correct the 64-byte documentation error; then re-classify APPROVED.

### Probe 3: HS I / LCDV2-declared GetSerialNumber (A-class)

**Cmd byte:** 0x88 (decimal 136)
**Framing class:** A
**Source family / hypothesis:** HydroShift LCD (HS I) and LCDV2 both
declare `GetSerialNumber = 136`. LCDV2 marks it deferred (no codec in
the Phase 0d crate) and HS I has it enum-only with no call site. This
makes it the cleanest read-only probe LCDV2 hasn't yet exercised: if
the firmware returns a serial-like ASCII block, we close a Phase 1+
identity-read item with one round trip. If it returns nothing, we
learn that the byte is unimplemented on FW 1.6 - useful negative
information for the Phase 1 codec-coverage scope.
**Citation:** `L-Connect.Core/LConnectCore/Products/HydroShiftLCD/Commands.cs:23`
(`GetSerialNumber = 136`);
`L-Connect.Core/LConnectCore/Products/Galahad2Vision/Commands.cs:25`
(`GetSerialNumber = 136`); cross-referenced in
`docs/protocol/cross-device-survey/per-family/hydroshift-lcd.md:169`
and `docs/protocol/cross-device-survey/per-family/galahad2-vision.md:45`.
**Read/write classification:** read (`Get*` prefix; sibling pair
137 is the corresponding `SetSerialNumber` write, confirming the 136/
137 pair follows LCDV2's standard `Get*`/`Set*` pairing convention).
**Why we expect this to be safe:** Bare A-class request (`Length=0`,
empty Data). Even if the firmware does not implement the byte, no
state mutation is possible - no write payload is sent.
**Expected response shape if hypothesis holds:** A-class echo with
ASCII serial bytes in Data, terminated either by length or by a
sentinel. If the HS I pattern transfers, the response may span two
A-packets (mirroring `GetFirmwareVersion`'s two-packet ASCII
demuxing), so the probe may need a follow-up read - the current
`run_probe` returns only the first packet, which we accept as
sufficient signal for this drafting round.
**Failure mode if hypothesis fails:** Empty echo, timeout, or stale
cmd byte discarded by the drain.
**Run command:** `cargo run -q -p verify-galahad -- probe 0x88 --framing a --yes-read-only`
**hid-safety-reviewer classification:** APPROVED
**hid-safety rationale:** Three independent same-MCU citations: HydroShiftLCD/Commands.cs:23 (GetSerialNumber=136, HS I), Galahad2Vision/Commands.cs:25 (GetSerialNumber=136, LCDV2 itself), Galahad2Trinity/Commands.cs:14 (ReadSerialNumber=136). All three Winbond/Nuvoton 0x0416 families agree. Paired write cmd 137 (SetSerialNumber/WriteSerialNumber) on all families. Cmd 136 declared in LCDV2 command enum (crates/protocol/src/galahad2_lcdv2/commands.rs:48) with no codec yet - not a Phase 0d duplicate. A-class framing correct.

### Probe 5: TLLCD ReadSerialNumber - per-fan addressing read (B-class)

**Cmd byte:** 0x3E (decimal 62)
**Framing class:** B
**Source family / hypothesis:** TLLCD. TLLCD's cmd 62
`ReadSerialNumber` returns 34 bytes: 32-byte ASCII serial + Port
(0..3) + Index (0..2). The byte itself is interesting because TLLCD
uses it as the per-fan-screen identity-read - the `Get*`/`Read*`
prefix is the LCD-side analogue of LCDV2's deferred cmd 136
`GetSerialNumber`. Probing this byte against LCDV2 distinguishes
"LCDV2 honours both 0x88 and 0x3E for serial-read" (high info)
vs "LCDV2 honours only 0x88" (mild info) vs "LCDV2 honours
neither" (negative-info, narrows the address space). Cross-MCU
prior is low.
**Citation:** `L-Connect.Core/LConnectCore/Products/TLLCD/LCDCommands.cs:15`
(`ReadSerialNumber = 62`); response decoder
`L-Connect.Core/LConnectCore/Products/TLLCD/SerialNumberInfo.cs:36-53`;
cross-referenced in
`docs/protocol/cross-device-survey/per-family/tllcd.md:150, 167-191`.
**Read/write classification:** read (`Read*` prefix; sibling pair 63
is the corresponding `WriteSerialNumber` write).
**Why we expect this to be safe:** Bare B-class request with empty
payload. No state mutation is possible.
**Expected response shape if hypothesis holds:** B-class echo with
ASCII bytes in Data, possibly with port/index trailer bytes.
**Failure mode if hypothesis fails:** Empty echo, timeout, or stale
cmd byte discarded by the drain.
**Run command:** `cargo run -q -p verify-galahad -- probe 0x3E --framing b --yes-read-only`
**hid-safety-reviewer classification:** APPROVED
**hid-safety rationale:** TLLCD/TLLCDDevice.cs:146-174. GetPortAndIndex() calls writeCommand(62,false) - bare read, no payload. Paired write is cmd 63 (TLLCDDevice.cs:282-289), not cmd 62. TLLCD host may call cmd 63 as recovery if port/index response invalid - this is host-side logic, not a cmd-62 side effect; the probe sends only cmd 62 once. Framing: TLLCD T-class=512 bytes out, probe sends LCDV2 B-class=1024 bytes - different shapes but cmd 62 not in LCDV2 enum so worst case is no response. Read*/Write* 62/63 mirrors LCDV2 Get*/Set* 136/137. APPROVED.

## Cross-cutting findings

1. **A-class parser is permissive / acts as universal echo.** Every
   A-class request sent (probes 1, 3) got a structured response with
   the standard `[01, cmd, ?, ?, ?, length, payload..., 0...]` shape,
   regardless of whether the cmd byte is in LCDV2's known enum. The
   `length` byte appears to communicate the response slot size that
   the firmware reserves for that cmd (8 bytes for cmd 0x8c, 32 for
   cmd 0x88), even if no actual data is populated.

2. **B-class parser is strict / silent on unknown.** Every B-class
   request to a cmd byte not in LCDV2's verified-live enum (probes 2,
   4, 5, 6) timed out without any device response.

3. **Asymmetric design rationale.** A-class is the small-packet
   query/control channel where capability discovery is desirable;
   B-class is the bulk-image-upload channel where strict cmd-byte
   gating prevents accidental writes. Phase 1 daemon should match this
   contract: probe with A-class, write structured B-class transfers
   only with verified cmd bytes.

4. **Cmd 15 activation hypothesis remains open but constrained.**
   Cmd 15 (UploadJpeg, B-class) is in LCDV2's enum and Phase 0d
   confirmed it accepts 56-packet writes without errors. The probe
   results don't directly resolve activation, but the cross-family
   pattern (sibling slv3/lcd207 SDKs use a filename-keyed activation
   path on a separate cmd byte) is the strongest hypothesis. Phase 0e
   declines to chase activation further; Phase 1 may revisit if
   needed.

5. **No bricking, no firmware corruption, no LED/LCD/RPM artifacts.**
   The hid-safety classification held: every probe was read-only in
   practice as well as on paper.
