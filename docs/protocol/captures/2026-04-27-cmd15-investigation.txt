Background
----------
Phase 0e closed the cross-family classification of cmd 15: it is
a transient PushJpg + stored UpdateFireWare with a filename pattern
(see docs/protocol/cross-device-survey.md section 6.5). What remains
unknown for the LCDV2 specifically is the *activation* mechanism --
when does a successfully uploaded cmd-15 image actually render on
the LCD?

Two hypotheses are open:

(a) Boot-time display: cmd 15 writes a stored image. The firmware
    renders it on next power-cycle (or USB resume from suspend).
    A "boot logo" / "splash" path. If true, exposing this through
    a future `lconnectctl lcd boot-image <PATH>` is a clean Phase 3
    feature.

(b) Sibling activate cmd: similar to slv3/lcd207's filename-keyed
    UpdateFireWare. After cmd 15, a second cmd writes a marker
    that selects which uploaded image is "active". The Phase 0e
    cross-family survey strongly suggests slv3 / lcd207 work this
    way, but the LCDV2-specific activate cmd has not been
    identified.

Safety notes
------------
- Cmd 15 is currently sealed off from the IPC surface (set_lcd_image
  only invokes cmd 14 SendJpeg). Verify-galahad is the only path
  that can reach cmd 15. Do not lift the IPC seal until activation
  is understood and the user has explicitly opted in.

- The cross-device survey notes (section 6.5) classified cmd 15 as
  "stored write" with no observed bricking risk in the LCDV2
  family. The Phase 0e probes against the user's device produced
  no visible behaviour change after the upload, so a single test
  pass is presumed safe to retry.

- Do not power-cycle the host while a cmd-15 upload is in flight.
  Wait for verify-galahad to print success before cycling.
