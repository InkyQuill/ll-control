# OUTCOME: BOTH cmd 131 (SetPumpLighting) and cmd 133 (SetFanLighting)
# produce visible LED changes on the LCDV2 — the pump cap went magenta
# under `--scope outer` and the fans went blue. The earlier "vestigial"
# hypothesis (based on the Vision controller's UI preferring cmd 20 /
# SetLEDColors / BCommandPacket for its dynamic effects) was wrong. Cmd
# 131 IS functional on this firmware; the visible LED region for the
# LCDV2 is the OUTER scope, not Inner (the default). `--scope inner`
# silently targets a region this SKU doesn't expose, which is why the
# initial test runs appeared dark.

## set-pump-lighting / set-fan-lighting

Wrote 64 bytes successfully on cmd 131 (SetPumpLighting) and cmd 133
(SetFanLighting) for several mode/colour/scope combinations:
- mode=StaticColor color=#FF0000 scope=Inner  (no visible change)
- mode=StaticColor color=#00FF00 scope=Inner  (no visible change)
- mode=Rainbow     speed=50      scope=Inner  (no visible change)
- mode=StaticColor color=#FF00FF scope=All    (no observation captured at the time)
- mode=StaticColor color=#FF00FF scope=Outer  (PUMP CAP WENT MAGENTA — visible!)
- (fan side) mode=StaticColor color=#0000FF   (FANS WENT BLUE — visible!)

So cmd 131 is functional on the LCDV2; the visible LED region is targeted
by `--scope outer` (or `--scope all`), NOT `--scope inner`. The default
`--scope inner` silently targets a region the LCDV2 SKU doesn't expose,
which is why the early test runs all looked dark. Updating the verify-
galahad CLI default to `--scope outer` would make the smoke test
visible-by-default, but `inner` matches the C# `PumpLightingScope` enum
default and faithfully ports the wire format — so the right fix is to
document the scope semantics rather than override them.

This refines (not contradicts) the earlier finding from
Galahad2VisionController.cs:1381-1414: the Vision UI uses cmd 20
(SetLEDColors, BCommandPacket — Phase 0d) for its dynamic per-pixel
effects, but cmd 131's preset-mode path is independently functional on
the same firmware and reaches the same outer LED ring.

## Notes

- Both Get* responses round-tripped on the first try once the
  verify-galahad CLI was updated to drain stale buffered responses
  (read_until_command helper); prior to the fix, the FIRST
  read_timeout after opening the device returned a stale response
  from a prior CLI invocation roughly half the time, surfacing
  errors like `expected 0x82, got 0x81`,
  `expected 0x84, got 0x82`, and `expected 0x82, got 0x84`.
- After the fix, post-fix verification across 5 sequential
  get-fan-lighting runs caught the helper draining 2 stale packets:
  one cmd 0x86 (GetFirmwareVersion echo) and one cmd 0x8e
  (ResetDevice echo, an unsolicited status packet — see
  galahad2-lcdv2.md "Real-hardware quirks (FW 1.6)" for the
  GetFirmwareVersion section, which already documents the
  cmd-0x8e quirk). The remaining 3 runs were clean. Helper
  behaviour is correct.
- max_speed = max_brightness = 4 confirms the C# UI's percent / 25
  wire-mapping (0..=100 percent → 0..=4 wire byte).
- The 16-mode pump list and 6-mode fan list match the
  PumpLightingMode / FanLightingMode enum coverage in
  crates/protocol/src/galahad2_lcdv2/lighting_enums.rs.
- Tried `--scope outer` and `--scope all` on cmd 131 in addition
  to the default `--scope inner`; no visible LED change observed
  for any scope value, consistent with the LCDV2 caveat above.
