## Family: UniversalScreen 8.8"

**Source folder:** `LConnectCore/Products/UniversalScreen8p8Inch/` (codec/data) and `LConnectService/Products/UniversalScreen8p8Inch/UniversalScreen8p8InchController.cs` (transport via SDK).
**Marketed name(s):** Lian Li Universal Screen 8.8" — large external 1920x480 RGBA LCD module with a surrounding addressable RGB ring; ships with companion lighting controller and (in some configurations) a CH340-class USB-to-serial display-mode pass-through.
**ControllerTypeID enum value(s):** three entries — `UniversalScreen8p8Inch = 17043456`, `UniversalScreen8p8InchDisplayMode = 17043457`, `UniversalScreen8p8InchLighting = 17043458` (`L-Connect.Core/LConnectCore/Devices/ControllerTypeID.cs:37-39`). All three are also enumerated in the `ControllerTypeIDDefinitions.cs:90` class mask.
**USB VID:PIDs (three sibling endpoints, one logical product):**
- Main display path: `0x1CBE:0xA088` (decimal `7358:41096`) — `KnownDevices.cs:77`. Vendor `0x1CBE` is Lumissil/ISSI / OEM-class, *not* the usual Lian-Li vendor.
- Display-mode (UART bridge): `0x1A86:0xAD21` (decimal `6790:44321`) — `KnownDevices.cs:79`. Vendor `0x1A86` is **WCH/QinHeng (CH340 USB-to-serial)** — confirms a CDC-ACM / serial pass-through transport for the display-mode SKU, distinct from the main HID-class endpoint.
- Lighting board: `0x0416:0x8050` (decimal `1046:32848`) — `KnownDevices.cs:81`. Same Nuvoton/Winbond VID as the Galahad II family lighting MCUs. **OpenRGB `LianLiUniversalScreenController` matches this PID exactly** (cross-survey section 5.3).

Only the main `0x1CBE:0xA088` PID is registered for WMI auto-discovery (`USBDeviceFinder.cs:23`); the two siblings are bound dynamically by the SDK once the parent controller is instantiated.

**Framing classes used:** **family-specific — no LCDV2 A/B/C framing on any of the three endpoints.** The L-Connect3 source does **not** construct USB packet bytes for this family at all: every device-touching call goes through opaque methods on the proprietary `slv3.dll` SDK (`LConnectService/Products/UniversalScreen8p8Inch/UniversalScreen8p8InchController.cs:14`, `using slv3;` / `using slv3.models;`). The C# layer only marshals semantic objects (`LightEffectSet`, sensor `Dictionary<string,double>`, byte[] firmware paths, `Bitmap` framebuffers) into and out of the SDK; the wire framing is wholly inside `slv3.dll`.

For the **lighting** sub-board, OpenRGB has independently reverse-engineered the wire path and confirmed it is a fourth framing class: `libusb_bulk_transfer` on **endpoint 1**, **64-byte flat packets**, no ReportID, no Length field, no PacketNumber, with chunk header `[0x11, offset, 0x00, 0x00, RGB...]` and a 20-LED-per-chunk stride. Per-LED byte order is **RGB** (not the Strimer Plus RBG quirk). Cross-validation table and citations are in `docs/development/protocol/cross-device-survey.md` section 5.3 (committed `5c58564`); the byte-level table is **not duplicated here**.

**Phase 0d status:** static-analysis only — distinct USB vendor IDs from LCDV2, no captured traffic, and the device path is mediated by a closed-source SDK. Not in ll-control scope until Phase 1+.

**Subsystem fingerprint:**
- Sensors / handshake (device-side): no — the device exposes no sensor read; instead the **host** gathers sensor values (`SystemInformation.Resource.*`) and **pushes** them into `sdkController.UpdateSensorValues(dictionary)` (`UniversalScreen8p8InchController.cs:6225`) which returns a rendered `Bitmap` of the active template/modular layout. Sensor-value channel set covers CPU/GPU temp/clock/load/power/fan/voltage, GPU memory, drive temp/usage/load, network up/down, RAM, PUMP/WATERPUMP RPM, FPS metrics, plus string channels CPUMODEL/GPUMODEL/FPS_TARGET_APP_NAME (`UniversalScreen8p8InchController.cs:6113-6192`).
- Serial number / identification: `GetScreenSerialNumber` and `GetLightingSerialNumber` are surfaced as separate request types (`UniversalScreen8p8InchRequestType.cs:7-8`) — read via SDK (`get_SN()`), not via a custom command-byte handshake.
- Firmware version: `GetFirmwareVersion` (req 3) returns string `lianli88_NNNN_NNNN`; `UniversalScreen8p8InchFirmwareVersion.cs:10-46` parses the trailing 4 digits via regex, subtracts 8, then maps to `Version(major = (n-8)/10, minor = (n-8)%10)`. There is also a **separate** `LightingFirmwareVersion` for the lighting MCU (`UniversalScreen8p8InchLightingFirmwareVersion.cs`).
- Firmware update: `StartFirmwareUpdate` (req 4) takes a host-side file path and forwards to `sdkController.FirmwareUpdate(path)` (`UniversalScreen8p8InchController.cs:6072`); `CheckFirmwareUpdateStatus` (req 5) polls progress. Display-mode-only.
- Fan PWM / pump PWM: **N/A** — no fans or pump on the device; PUMP/WATERPUMP appear only as host-supplied sensor *values* fed into the rendered overlay.
- LCD on/off / brightness / rotation: yes — `SetScreenBrightness` (req 23, range 0..=100; `Constants.cs:9-11`) -> `sdkController.SetBrightness` (`UniversalScreen8p8InchController.cs:5548`); `SetScreenOrientation` (req 25, landscape/portrait) and `SetScreenRotation` (req 27, 180-deg flip) -> `sdkController.Rotate(num)` (`UniversalScreen8p8InchController.cs:5773`).
- LCD frame upload: yes, but **not as discrete protocol commands**. The render pipeline is:
  1. Apply a template via `sdkController.ApplyTemplate(theme)` (`UniversalScreen8p8InchController.cs:487`) and start the render loop with `StartScreenRender` (req 21).
  2. The host's sensor loop pushes values to the SDK; the SDK returns a 1920x480 BGRA `Bitmap` (`UpdateSensorValues`, `:6225`).
  3. `Marshal.Copy` lifts the bitmap into a fixed `screenFrameBuffer = new byte[3686400]` (1920 * 480 * 4 = 3,686,400 — confirms BGRA32 layout) (`UniversalScreen8p8InchController.cs:120,6238-6240`).
  4. The framebuffer is shipped to the GUI process via cross-process `WriteProcessMemory`-style `copyImageMemory(processId, destAddress, sourceBuffer)` (`UniversalScreen8p8InchController.cs:932`, `4293`, `4352`) — this is host-host IPC, not USB. The actual USB frame upload to the panel happens *inside* `slv3.dll` and is **not visible in the L-Connect3 source**.
  5. `StopScreenRender` (req 22) tears the loop down (`UniversalScreen8p8InchController.cs:5920` -> `sdkController.StopEffect()`; `:6008` -> `PlayStop()`).
- Lighting (preset effect modes): yes — 19 modes in `UniversalScreen8p8InchLightingMode.cs:5-26` (Rainbow, Wave, StaticColor, Breathing, RainbowMorph, Paint, Runway, Tide, BlowUp, Meteor, Snooker, Mixing, PingPong, BulletStack, Twinkle, River, Hourglass, ElectricCurrent, RainbowWave). Mapped to SDK `RgbEffectTypes` via `lightingModeMapping` (`UniversalScreen8p8InchController.cs:158, 871`). Setting payload (`UniversalScreen8p8InchLightingSetting.cs:11-33`) is `{ Brightness 0..=100, Speed 0..=100, Colors[], IsReverseDirection }`. Brightness is rescaled host-side `0..100 -> 0..255` and speed is rescaled `0..100 -> 7..3` (low_speed=7, high_speed=3, *inverted* — bigger SDK value = slower) (`UniversalScreen8p8InchController.cs:142-148, 853, 863`). Direction: 0/1 (`:889`).
- Lighting (per-LED RGB): the LCDV2-style "set LED colors" path is *not* exposed as a command in L-Connect3. The lighting MCU's per-LED RGB stream is driven by OpenRGB-confirmed `0x11`-header bulk packets on EP1 (cross-survey section 5.3); the L-Connect3 service does not call this path directly — it relies on the SDK firmware-mode lighting only.
- Continuous re-issue / polling pattern: yes — periodic readers for both `screenSerialNumberReaderTimer` and `lightingSerialNumberReaderTimer` at 1-second cadence (`UniversalScreen8p8InchController.cs:32, 38, 40, 141`); the SDK's own internal timer drives `UpdateSensorValues` re-rendering at the 24 fps `ScreenFrameRate` constant (`Constants.cs:29`).
- Reset / soft-reset: `ResetProfile` (req 9) is a host-side profile clear, not a hardware reset. **No on-device reset command** is exposed via the L-Connect3 surface.
- Display-mode SKU vs main SKU: same product family, **gated by the boolean `isDisplayMode`** passed to the controller constructor (`UniversalScreen8p8InchController.cs:216-219`). The `checkIsDisplayMode(...)` guard (`:703-711`) returns `false` (i.e. "blocked") when the device *is* in display mode — i.e. most semantic ops (lighting, sensors, render, brightness, rotation, secondary screen, firmware update) require **non-display-mode**. Only the offline-clock op (`SetOfflineModeClock`, req 26) is the inverse: it requires *display-mode* (`UniversalScreen8p8InchController.cs:5666`).
- Crypto / obfuscation at HID transport: not observable from C# (entirely behind `slv3.dll`).

### Subsystem patterns

- **Three-endpoint architecture.** Unlike LCDV2 (one PID, one HID interface), the UniversalScreen 8.8" is a *cluster* of three USB devices that the SDK glues into a single logical product. The display panel speaks one protocol, the CH340-based "display mode" UART speaks another (likely AT-style serial commands), and the lighting MCU speaks the OpenRGB-discovered bulk-EP1 RGB protocol. Phase 1 ll-control work needs to enumerate and bind all three before any sensible feature surface is reachable.
- **LCD frame-upload is invisible to source.** The 1920x480x4 BGRA framebuffer is rendered host-side (by the SDK's `UpdateSensorValues`-returns-`Bitmap` call) and shipped to the LCD via SDK-internal USB transfers. There is **no `SendJpeg`/`SendH264Frame`/`SetLEDColors`-style command byte** exposed in C# for this family. Reverse-engineering Linux support for the LCD requires either (a) capturing the EP traffic from the panel PID `0x1CBE:0xA088` while the SDK is rendering, or (b) decompiling `slv3.dll`. Both are out of scope for this static survey.
- **Cross-process memory shipping.** `copyImageMemory(processId, destAddress, byte[] sourceBuffer)` (`UniversalScreen8p8InchController.cs:932`) is a one-way `WriteProcessMemory`-class IPC channel from L-Connect-Service to the L-Connect3 GUI process. Used for both screen top-layer (req 29) and theme-info preview (req 58). On Linux this is not portable; the daemon equivalent should expose the framebuffer over a shared-memory region or D-Bus byte stream instead.
- **Sensor flow is one-way host->device.** No on-device sensor *read*; the host (via `SystemInformation.Resource.*`) supplies the values that the SDK then renders into the next frame. Channels: 30+ named numeric channels and 3 string channels (`Controller.cs:6113-6192`). For ll-control this means LCD content is *purely* a host-driven render; we don't need to poll the device, but we do need a Linux-side equivalent of HWiNFO/PresentMon to feed values.
- **Non-monotonic speed encoding (lighting).** Host `Speed = 0..=100` is mapped to SDK `RFLampEffectSpeedType = 7..3` via `NumberHelper.ConstrainMap(value, 0, 100, 7, 3)` — i.e., **higher percentage -> *lower* SDK byte** (`Controller.cs:863`). This is yet another non-monotonic mapping on top of the Strimer Plus speed-table footgun; the llcontrol-protocol crate will need to surface this as a typed enum rather than a `0..255` byte.
- **24 fps fixed render rate.** `ScreenFrameRate = 24` (`Constants.cs:29`). Combined with the 1920x480x4 buffer this is a 169.7 MB/s host-side render budget; the actual USB throughput to the panel is whatever rate the SDK chooses internally.
- **Crop minimums.** `CropMinScreenLandscapeWidth/Height = 720/180`, portrait `180/720` (`Constants.cs:21-27`). Suggests the panel supports a subwindow / region-of-interest update path.
- **Firmware version oddity.** Two FW strings (panel + lighting MCU). Panel format `lianli88_NNNN_NNNN` with the trailing 4-digit field decoding to `Version((n-8)/10, (n-8)%10)` only when `n >= 18` (`FirmwareVersion.cs:38-45`). Treat versions below `0026` as invalid.

### Notable divergences from LCDV2

- **Framing class.** No A/B/C wire framing on any endpoint. The lighting board uses the OpenRGB-confirmed bulk-EP1 / 64-byte / `0x11`-header path (cross-survey 5.3), which becomes the survey's fourth framing class (provisionally `UniversalScreenBulk`). The display panel and the CH340 display-mode bridge use SDK-encapsulated formats not visible in this source.
- **No host-built packets.** Unlike Galahad II (where `Galahad2VisionDevice.cs` builds every byte) and Strimer Plus (where `StrimerPlusDevice.cs` builds the HID feature/output reports), the entire UniversalScreen surface is mediated through `slv3.dll`. The ll-control port cannot copy bytes-for-bytes from this source tree; it must either consume OpenRGB's cross-validated lighting protocol or capture the LCD wire format afresh.
- **Sensor direction inverted.** LCDV2 cmd 129 reads sensors *from* the device. UniversalScreen pushes host-supplied sensor values *to* the device for rendering. Different abstraction entirely.
- **Frame-upload is not a discrete command.** LCDV2 has `SendJpeg` / `SendH264Frame` / `SetLEDColors` as explicit cmd-byte operations. UniversalScreen has none; the LCD content stream is a continuous SDK-internal pipe driven by `UpdateSensorValues` -> `Bitmap` -> opaque USB transfer.
- **Three USB IDs for one product.** LCDV2 is a single PID; UniversalScreen registers three. The CH340 PID on the display-mode SKU is the most surprising — it implies a fundamentally different transport (CDC-ACM serial), unlike anything else in the LConnect3 product matrix surveyed so far.
- **No reset / no soft-reset.** LCDV2's cmd 142 has no UniversalScreen equivalent; recovery is whatever the SDK does internally.

### Unclear flags

- Lighting wire bytes: documented in OpenRGB section 5.3, **not** in this source tree. Cross-validation from the L-Connect3 side is **not possible** — the byte construction lives inside `slv3.dll`. Status: **deferred to OpenRGB / live capture.** unclear-reason: closed-source SDK.
- Display panel (`0x1CBE:0xA088`) wire format: **completely undocumented from this source.** No OpenRGB coverage either. Phase 1 needs raw USB capture (Wireshark + usbmon) of the panel endpoint while L-Connect3 is rendering. unclear-reason: closed-source SDK + no community RE.
- Display-mode bridge (`0x1A86:0xAD21`, CH340 UART): unknown command set. Worth dumping the serial line at the host's COMx with a passive sniffer; the AT-style command set Lian-Li uses (if any) is undocumented. unclear-reason: closed-source SDK + UART-class device, not USB-class.
- `SetSecondaryScreen` (req 21, alias `SetDesktopMode`/`SetMonitorMode`): the boundary between "desktop clone" and "dedicated info-LCD" modes is ambiguous; the panel may enumerate as a Windows display device in one mode. Unverified. unclear-reason: SDK behaviour not visible.
- Lighting `Speed` / `Brightness` SDK-byte mapping (`0..100 -> 7..3` and `0..100 -> 0..255`): the inverted speed mapping is documented in source but its on-wire byte (post-SDK) is not. unclear-reason: SDK-internal translation may apply further mapping.
- `RgbEffectTypes` -> wire byte mapping: the static dictionary `lightingModeMapping` is initialized in a static constructor that the decompiler did not surface; the 19 host modes likely collapse to fewer SDK enum values. OpenRGB documents 16 mode bytes for the lighting controller (cross-survey 5.3); reconciling the 19 vs 16 needs live capture. unclear-reason: missing static-ctor decompile + closed-source SDK.

### Open questions for live capture (Phase 1+)

- Capture EP1/EP2/EP3 traffic on `0x1CBE:0xA088` while the SDK is rendering a known template at known sensor values. Goal: identify the LCD frame-upload command byte and chunk size, and whether it's JPEG/H.264/raw (the LCDV2 `SendJpeg` precedent suggests JPEG; the 24 fps target with 921,600-pixel raw frames at >150 MB/s argues for compression).
- Sniff the CH340 UART for the display-mode SKU. Likely an AT-style or printable-ASCII command set (CH340 is normally used for serial-bridge firmware update or low-bandwidth control).
- Cross-check OpenRGB's `M_*` lighting-mode enumeration against the 19 host modes in `UniversalScreen8p8InchLightingMode.cs`. Specifically: which host modes (Paint, Tide, BlowUp, Snooker, Mixing, PingPong, BulletStack, Twinkle, River, Hourglass, ElectricCurrent, RainbowWave) collapse onto which SDK / firmware bytes, and which are host-side animations baked into the rendered frame stream rather than firmware-resident effects.
- Verify whether `screenFrameBuffer` BGRA byte order is preserved on the wire or whether the SDK swaps to RGB / RGB565 / JPEG-encoded before transmit.
