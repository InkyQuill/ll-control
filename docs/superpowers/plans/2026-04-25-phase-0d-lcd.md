**Goal:** Land the LCD subsystem foundation: the **`BCommandPacket`** 1024-byte
output / 512-byte input framing primitive (with multi-packet chunking), the LCD
lifecycle commands (`IsLCDAvailable` cmd 23, `LCDControl` cmd 12), the
high-value **`SetLEDColors`** cmd 20 (per-pixel RGB control, used by the C#
UI for dynamic / animated effects on the LCDV2 LED ring), and a
working **JPEG upload pipeline** (`SendJpeg` cmd 14, `UploadJpeg` cmd 15).
H.264 streamed-frame upload (`SendH264Frame` cmd 13) is the stretch goal.
Firmware upload/activate (cmds 11/10) is **explicitly out of scope** —
deferred to Phase 1+ behind a feature flag with strong safety gates.

This phase does **not** depend on Phase 0c's cmd 131 being functional —
that command has been independently verified live on the LCDV2 against
multiple colours and the `--disable` path. The "transient buffering"
observation from Phase 0c (rapid-write storms can briefly stall renders
until firmware catches up) is what `:2443`'s timer in the C# service
likely papers over.

**Architecture:** Extends the Phase 0a/0b/0c pattern — pure
`crates/protocol/galahad2_lcdv2/` codecs with golden-byte tests, exercised
live via `verify-galahad`. The new structural primitive is `BCommandPacket`:
a 1024-byte HID output report (Report ID `0x02`) with an 11-byte header
(ReportID, Command, **32-bit big-endian DataSize**, **24-bit big-endian
PacketNumber**, **16-bit big-endian Length**) and up to 1013 bytes of
payload per packet. Multi-packet writes split a payload into 1013-byte
chunks, incrementing `PacketNumber` and replicating `Command` and
`DataSize` on every packet (so the device knows the total transfer size up
front). Inputs are 512 bytes (1 packet, since reads aren't chunked). The
codec lives in `crates/protocol/src/galahad2_lcdv2/bpacket.rs`; chunking is
exposed as an iterator-returning helper `BCommandPacket::build_packets_for_write`.

**Tech Stack:** Rust 1.92 / Edition 2021. Same workspace and dependencies as
Phase 0a/0b/0c. No new crates. JPEG bytes are passed through opaquely (we do
NOT introduce a JPEG encoder dependency in this phase — the verify-galahad
CLI takes a `--jpeg-path` and reads the file).

Sketch:

```rust
//! `BCommandPacket` — 1024-byte HID output / 512-byte input framing for
//! cmds that exceed the 58-byte ACommandPacket payload (image uploads,
//! per-pixel LED arrays, firmware blobs).
//!
//! Source: Products/Galahad2Vision/BCommandPacket.cs:1-189.

/// HID Report ID byte for B-class output packets.
pub const B_REPORT_ID: u8 = 0x02;
/// Output packet length on the wire (host → device).
pub const B_OUTPUT_LEN: usize = 1024;
/// Input packet length on the wire (device → host).
pub const B_INPUT_LEN: usize = 512;
/// Header bytes preceding the payload.
pub const B_HEADER_LEN: usize = 11;
/// Maximum payload bytes per packet.
pub const B_PAYLOAD_MAX: usize = B_OUTPUT_LEN - B_HEADER_LEN; // 1013

// Big-endian header field offsets (matches C# bit-shifts):
const OFF_DATA_SIZE_HI: usize = 2;   // 4 bytes [2..6]
const OFF_PACKET_NUMBER: usize = 6;  // 3 bytes [6..9]
const OFF_LENGTH: usize = 9;         // 2 bytes [9..11]

/// One B-class HID output packet, 1024 bytes wide.
#[derive(Debug, Clone)]
pub struct BCommandPacket {
    bytes: [u8; B_OUTPUT_LEN],
}

impl BCommandPacket {
    /// Build a single B-packet for transmission.
    ///
    /// Caller is responsible for providing the correct `data_size` (total
    /// across all chunks) and `packet_number`; the chunker in
    /// [`build_packets_for_write`] handles both for you.
    pub fn new_request(
        command: u8,
        packet_number: u32,
        payload: &[u8],
        data_size: u32,
    ) -> Self {
        let mut bytes = [0u8; B_OUTPUT_LEN];
        bytes[0] = B_REPORT_ID;
        bytes[1] = command;
        bytes[OFF_DATA_SIZE_HI..OFF_DATA_SIZE_HI + 4]
            .copy_from_slice(&data_size.to_be_bytes());
        // 24-bit BE PacketNumber: take the low 3 bytes of the u32.
        let pn = packet_number.to_be_bytes();
        bytes[OFF_PACKET_NUMBER..OFF_PACKET_NUMBER + 3]
            .copy_from_slice(&pn[1..4]);
        let n = payload.len().min(B_PAYLOAD_MAX);
        let length_be = (n as u16).to_be_bytes();
        bytes[OFF_LENGTH..OFF_LENGTH + 2].copy_from_slice(&length_be);
        bytes[B_HEADER_LEN..B_HEADER_LEN + n].copy_from_slice(&payload[..n]);
        Self { bytes }
    }

    /// Borrow the packet as the 1024-byte buffer ready for `hid_device.write(...)`.
    pub fn as_bytes(&self) -> &[u8; B_OUTPUT_LEN] {
        &self.bytes
    }

    /// Parse and validate an inbound B-class response (typically 512 bytes).
    pub fn from_response<'a>(
        buf: &'a [u8],
        expected_command: u8,
    ) -> crate::Result<BResponse<'a>> {
        if buf.len() < B_HEADER_LEN {
            return Err(crate::Error::BufferTooShort {
                need: B_HEADER_LEN,
                got: buf.len(),
            });
        }
        if buf[0] != B_REPORT_ID {
            return Err(crate::Error::UnexpectedReportId {
                expected: B_REPORT_ID,
                got: buf[0],
            });
        }
        if buf[1] != expected_command {
            return Err(crate::Error::UnexpectedCommand {
                expected: expected_command,
                got: buf[1],
            });
        }
        let data_size = u32::from_be_bytes([buf[2], buf[3], buf[4], buf[5]]);
        let packet_number =
            u32::from_be_bytes([0, buf[6], buf[7], buf[8]]);
        let length = u16::from_be_bytes([buf[9], buf[10]]) as usize;
        if length > B_PAYLOAD_MAX {
            return Err(crate::Error::InvalidLength {
                length,
                max: B_PAYLOAD_MAX,
            });
        }
        if buf.len() < B_HEADER_LEN + length {
            return Err(crate::Error::BufferTooShort {
                need: B_HEADER_LEN + length,
                got: buf.len(),
            });
        }
        Ok(BResponse {
            command: buf[1],
            data_size,
            packet_number,
            length,
            data: &buf[B_HEADER_LEN..B_HEADER_LEN + length],
        })
    }
}

/// View into a parsed B-class response. Borrows from the input buffer.
#[derive(Debug, Clone, Copy)]
pub struct BResponse<'a> {
    command: u8,
    data_size: u32,
    packet_number: u32,
    length: usize,
    data: &'a [u8],
}

impl<'a> BResponse<'a> {
    /// Echoed command byte from the response.
    pub fn command(&self) -> u8 { self.command }
    /// Total payload size announced by the device (32-bit).
    pub fn data_size(&self) -> u32 { self.data_size }
    /// 0-based packet index in this transfer (24-bit).
    pub fn packet_number(&self) -> u32 { self.packet_number }
    /// Bytes-of-payload in this packet (16-bit).
    pub fn length(&self) -> usize { self.length }
    /// Payload slice, exactly `length` bytes.
    pub fn data(&self) -> &'a [u8] { self.data }
}
```

### Task 2: Add the multi-packet chunker `build_packets_for_write`

The `SetLEDColors`, `SendJpeg`, `UploadJpeg`, `SendH264Frame` commands
all submit payloads that may exceed 1013 bytes. The C# uses an iterator
(`BuildPacketsForWrite`) that yields one packet per chunk, replicating
`Command` and `DataSize` and incrementing `PacketNumber` from 0. We
mirror that with an iterator-returning helper.

**Files:**
- Modify: `crates/protocol/src/galahad2_lcdv2/bpacket.rs`
- Modify: `crates/protocol/tests/galahad2_lcdv2_bpacket.rs` (append)

**Before-you-implement:** the C# `BuildPacketsForWrite`
(`BCommandPacket.cs:145-175`) reuses a *single* `bCommandPacket1` buffer
and yields it repeatedly through the iterator (mutating `bytes` in
place between yields). **The Rust port MUST NOT replicate this buffer
reuse.** A naive port that returns `&[u8; 1024]` slices into a shared
buffer would produce aliased references — invalid in Rust and a
correctness bug if any caller collects iterator output (e.g.
`.collect::<Vec<_>>()` or stages chunks for batched submission). The
Rust chunker MUST produce **independent owned buffers** — yield owned
`BCommandPacket` values per iteration (each carrying its own `[u8;
1024]`), so callers can collect into `Vec<BCommandPacket>` /
`Vec<[u8; 1024]>` without aliasing. The cost (1 KiB clone per chunk)
is negligible versus the actual HID write.

Keep the empty-payload case: a single packet with `DataSize=0`,
`PacketNumber=0`, `Length=0`.

```rust
impl BCommandPacket {
    /// Iterator over B-packets to write to the device for a payload of
    /// arbitrary size. Empty payload → single packet with `DataSize=0`.
    /// Otherwise, payload is split into 1013-byte chunks; every packet
    /// replicates `command` and `data_size = payload.len()`, and
    /// `packet_number` increments from 0.
    ///
    /// Mirrors `BCommandPacket.cs:145-175` (`BuildPacketsForWrite`).
    pub fn build_packets_for_write<'a>(
        command: u8,
        payload: &'a [u8],
    ) -> BPacketChunks<'a> {
        BPacketChunks {
            command,
            payload,
            data_size: payload.len() as u32,
            cursor: 0,
            emitted_empty: false,
        }
    }
}

/// Iterator returned by [`BCommandPacket::build_packets_for_write`].
pub struct BPacketChunks<'a> {
    command: u8,
    payload: &'a [u8],
    data_size: u32,
    cursor: usize,
    emitted_empty: bool,
}

impl<'a> Iterator for BPacketChunks<'a> {
    type Item = BCommandPacket;

    fn next(&mut self) -> Option<Self::Item> {
        if self.payload.is_empty() {
            if self.emitted_empty {
                return None;
            }
            self.emitted_empty = true;
            return Some(BCommandPacket::new_request(self.command, 0, &[], 0));
        }
        if self.cursor >= self.payload.len() {
            return None;
        }
        let pn = (self.cursor / B_PAYLOAD_MAX) as u32;
        let end = (self.cursor + B_PAYLOAD_MAX).min(self.payload.len());
        let chunk = &self.payload[self.cursor..end];
        self.cursor = end;
        Some(BCommandPacket::new_request(
            self.command,
            pn,
            chunk,
            self.data_size,
        ))
    }
}
```

## Part C — `SetLEDColors` (cmd 20) — the high-value unlock

### Task 5: TDD `SetLEDColors` codec

The per-pixel pump-cap LED driver: cmd 20 paints individual RGB values
into the screen / fan LED rings, which is the path the C# UI uses for
dynamic and animated effects. (Cmd 131 / `SetPumpLighting` from Phase
0c handles preset modes — both commands are independently functional;
the rendering paths are parallel, not gated on one another.)

**Critical wire-layout note:** the very first byte of the payload is
`r[0] = (byte)isFanLed` — a flag byte at offset 0 distinguishing the
fan-ring path (`0x01`) from the screen / pump-cap path (`0x00`). The
RGB pixel data does NOT start at offset 0; it starts at offset 1 for
fan, offset 25 for screen (after a 24-byte zero pad sitting between
the flag byte at offset 0 and the pixel data at offset 25).

The full layout (from `Galahad2VisionDevice.cs:283-308`):

```text
isFanLed=true (fan ring):
  offset 0:        isFanLed flag byte = 0x01
  offset 1..:      R0, G0, B0, R1, G1, B1, ..., Rn-1, Gn-1, Bn-1
  total length =   colors.len() * 3 + 1

isFanLed=false (screen / pump-cap):
  offset 0:        isFanLed flag byte = 0x00
  offset 1..25:    24 bytes of zero pad (8 extra Color slots × 3 channels)
  offset 25..:     R0, G0, B0, R1, G1, B1, ..., Rn-1, Gn-1, Bn-1
  total length =   (colors.len() + 8) * 3 + 1
  // C# index `num` starts at 25, leaving bytes 1..25 as zero pad.
```

Byte-by-byte payload table (screen-LED variant, n LEDs):

| offset    | size    | content                                |
|----------:|--------:|----------------------------------------|
| 0         | 1       | `isFanLed` flag byte (= `0x00`)        |
| 1..25     | 24      | zero pad (8 padding Color slots × 3)   |
| 25..25+3n | 3*n     | RGB triples `R0,G0,B0,...,Rn-1,Gn-1,Bn-1` |

Byte-by-byte payload table (fan-LED variant, n LEDs):

| offset    | size    | content                                |
|----------:|--------:|----------------------------------------|
| 0         | 1       | `isFanLed` flag byte (= `0x01`)        |
| 1..1+3n   | 3*n     | RGB triples `R0,G0,B0,...,Rn-1,Gn-1,Bn-1` |

We model the two cases as two builder functions:
`build_set_fan_led_colors_request(colors)` and
`build_set_screen_led_colors_request(colors)`.

```rust
//! SetLEDColors (cmd 20). The actual per-LED RGB array driver — both for
//! the fan ring and for the pump-cap screen LEDs.
//!
//! Source: Galahad2VisionDevice.cs:283-308. The fan-LED path is a simple
//! `[0x01, R0, G0, B0, ...]` array; the screen-LED path prepends a 24-
//! byte zero pad after the isFanLed=0 byte (so RGB data starts at offset
//! 25 of the payload).

use crate::galahad2_lcdv2::bpacket::{BCommandPacket, B_OUTPUT_LEN};
use crate::galahad2_lcdv2::commands::Command;
use crate::galahad2_lcdv2::lighting::Rgb;

/// Build the fan-LED payload (isFanLed=true). Layout:
/// `[0x01, R0, G0, B0, R1, G1, B1, ...]`. Length = `colors.len() * 3 + 1`.
pub fn fan_led_payload(colors: &[Rgb]) -> Vec<u8> {
    let mut out = Vec::with_capacity(1 + colors.len() * 3);
    out.push(0x01);
    for c in colors {
        out.extend_from_slice(&[c.r, c.g, c.b]);
    }
    out
}

/// Build the screen-LED payload (isFanLed=false). Layout:
/// `[0x00, <24 zero bytes>, R0, G0, B0, ...]`. Length =
/// `(colors.len() + 8) * 3 + 1`.
pub fn screen_led_payload(colors: &[Rgb]) -> Vec<u8> {
    let mut out = vec![0u8; (colors.len() + 8) * 3 + 1];
    out[0] = 0x00;
    let mut idx = 25;
    for c in colors {
        out[idx] = c.r;
        out[idx + 1] = c.g;
        out[idx + 2] = c.b;
        idx += 3;
    }
    out
}

/// Build SetLEDColors B-packets for the fan ring path.
pub fn build_set_fan_led_colors_request(colors: &[Rgb]) -> Vec<[u8; B_OUTPUT_LEN]> {
    let payload = fan_led_payload(colors);
    BCommandPacket::build_packets_for_write(Command::SetLEDColors as u8, &payload)
        .map(|p| *p.as_bytes())
        .collect()
}

/// Build SetLEDColors B-packets for the screen / pump-cap LEDs.
pub fn build_set_screen_led_colors_request(colors: &[Rgb]) -> Vec<[u8; B_OUTPUT_LEN]> {
    let payload = screen_led_payload(colors);
    BCommandPacket::build_packets_for_write(Command::SetLEDColors as u8, &payload)
        .map(|p| *p.as_bytes())
        .collect()
}
```

**Real-hardware findings on FW 1.6 (LCDV2):**

- **Cmd 14 (`SendJpeg`) is transient single-frame** with ~20-second
  mode-independent auto-revert to LocalUI default. The C# `VideoFPS=24`
  field is consistent with a continuous-frame architecture; sustained
  static-image display needs a daemon refresh loop at ≤15-second
  intervals.
- **Cmd 15 (`UploadJpeg`) accepts 56-packet writes in full but does
  not visibly render to the LCD**, with or without
  `LCDControl{mode=Application}` preflight. Activation path unknown —
  possibly stored to flash for boot/startup display, possibly requires
  an undiscovered trigger command, possibly used by an internal
  display mode (LocalAVI, LocalH264) we have not activated. Recommend:
  do not use cmd 15 in production daemon code until the activation
  path is discovered.
- **Cmd 20 (`SetLEDColors`) supersedes cmd 131 (`SetPumpLighting`) in
  the LED render pipeline.** Per-pixel updates beat preset modes; the
  C# UI's pattern of using cmd 20 for dynamic effects is consistent
  with this.
- **Multi-packet BCommandPacket transfers are robust** at 21, 46, and
  56 packets without tearing or partial-frame artifacts.
- **`LCDControlMode::Application`** does NOT change cmd 14's hold time
  (early test was misread). Application mode may have other effects
  we haven't characterized.
- **The `lconnect-image` pipeline produces visually-good output**
  across smooth gradients, photographic content, and text/sharp-edge
  imagery at quality 90 + FitMode::Crop. JPEG sizes ranged 20-56 KiB
  for the test corpus.
